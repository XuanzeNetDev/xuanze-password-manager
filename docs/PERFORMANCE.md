# 璇泽密钥库 · 性能报告

> 机器：Windows / AMD Ryzen（32 逻辑核）/ Rust 1.100
> 构建：`release`（`opt-level=3`, `lto="fat"`, `codegen-units=1`, `panic="abort"`）
> 复现：`cargo run --release -p xz-bench`

---

## 1. 设计前提

密码管理器的性能问题只有一个真问题：**用户每次击键都要看到结果**。

所以我们把时间轴切成两段：

| 阶段 | 频率 | 目标 |
|---|---|---|
| 打开 vault（KDF + 解密 + 建索引） | 每会话一次 | 允许 100 ms 级，用户能接受「输密码 → 稍等」 |
| 打开之后的一切（搜索/复制/列表） | 每次击键 | **必须 < 5 ms**，理想 < 1 ms |

结论：**KDF 值得慢，其余一分一毫都不该慢**。下面的数字都是围绕这条原则调的。

---

## 2. KDF —— 打开时的固定成本

Argon2id，用 `argon2` crate 的默认（非多线程）实现。

| 档位 | 参数 | 中位耗时 |
|---|---|---:|
| `light` | 19 MiB × 2 轮 × 1 lane | **16 ms** |
| `balanced`（默认） | 64 MiB × 3 轮 × 4 lanes | **85 ms** |
| `paranoid` | 256 MiB × 4 轮 × 4 lanes | **510 ms** |

这一档就是打开 vault 的花费，没法再压——它是安全预算，不是性能缺陷。
默认选 `balanced`（OWASP 2024 推荐），并在 UI 上告诉用户「这个进度条是在做加密，
不是卡了」。

## 3. 高频路径（1 万条条目）

| 操作 | 耗时 | 说明 |
|---|---:|---|
| 取主秘密 `reveal_secret` | **44 ns** | 一次 `String` clone，无密码学 |
| 记录一次使用 `record_use` | **0.8 µs** | 索引增量更新，无重排 |
| 搜索·空查询（热度榜） | **21 µs** | 打开即是常用列表 |
| 搜索·模糊前缀 `ke` | **~62 µs** | 命中约 9000 条，Top-K 只留 80 |
| 搜索·全库无命中 | **~290 µs** | 最坏情况，全量遍历 |
| 搜索·精确命中 `key-004242` | **~450 µs** | 见下方「为什么精确查询反而更慢」 |
| 热度榜 top9 | **~22 µs** | `select_nth_unstable` 部分排序 |
| 中文查询（ASCII 为主的库） | **~680 µs** | |
| 中文查询（中文为主的库） | **~980 µs** | 无法再优化，见 §6 |

### 为什么「精确命中」比「模糊前缀」慢

反直觉，但完全合理：模糊前缀 `ke` 命中九千条，**窗口 80 个名额在头几百条就填满**，
之后每条只要比阈值差就直接丢；而精确查询在整个库里只命中 1 条，
窗口永远填不满，**每条都要走完预筛**。

也就是说，这个场景测的其实是「预筛跑满一万次」的成本，而不是排序成本。
真实使用中用户打的字越长命中越少、需要看的候选也越少，体验上并不会更差。

## 4. 全链路

| 条目数 | vault 体积 | 封存 | 打开（含 KDF） | 打开（净解析） | 保存（含 fsync） |
|---:|---:|---:|---:|---:|---:|
| 1 000 | 810 KiB | 3 ms | 18 ms | **2 ms** | 7 ms |
| 10 000 | 7.9 MiB | 41 ms | 56 ms | **39 ms** | 65 ms |
| 50 000 | 39.8 MiB | 206 ms | 249 ms | **228 ms** | 403 ms |

「净解析」= 打开耗时减去单独测得的 KDF 耗时，即 JSON 反序列化 + AES 解密 + 建索引。

3 万条以内（绝大多数个人库的真实规模）：**打开 100 ms 出头，保存 200 ms 以内**。

## 5. 优化过程（按时间顺序，含失败项）

这一节保留所有被推翻的尝试，因为「试过但没用」和「做对了」一样重要。

### 5.1 第一版：全量收集 + 部分排序

`Vec::push` 所有命中，再 `select_nth_unstable`。中文查询 1 万条命中九千条 →
九千次 push + 部分排序，**437 µs**。

### 5.2 流式 Top-K（保留）

定长窗口，满了之后只接受严格更好的，就地替换最差那条。
中文查询 437 µs → **318 µs**，且耗时与命中数量基本脱钩。

### 5.3 预小写副本（保留）

每次击键对全库 `to_lowercase` 是纯浪费。改成建索引时算一次，存进 `IndexItem`。
索引体积 +70%，搜索省掉上万次堆分配。

### 5.4 字节级预筛（保留）

打分前先做「有没有命中」的粗筛，命中才进完整打分。精确查询 759 µs → **371 µs**。

### 5.5 子序列并入预筛（保留）

`ghb` → `github` 这类模糊查询，如果在预筛层被否决就永远进不了 Top-K。
把子序列判定提到预筛层，代价是预筛多一次线性扫描，收益是这类查询从「查不出结果」
变成可用。实测子序列查询 322 µs。

### 5.6 手写 ASCII 不敏感子串查找（已回退）

想用一次扫描同时算「有没有命中」和「最好得多少分」，避开 `starts_with` +
`contains` + 子序列三次走查。我手写了逐字节循环做大小写不敏感匹配。

**结果更慢了。** 标准库的 `str::contains` 走 `memchr` 系的两路查找，
SIMD 优化过的；手写循环在短 needle 上完全打不过。回退。

教训：**不要跟标准库抢 memchr。** 需要不敏感匹配就用「预小写副本 + `contains`」。

### 5.7 CJK 早退窄化（已删除）

想给中文查询单独开一条路：先扫一遍全部名称做普通 `contains`，命中的才进完整打分。
设计依据是「中文库以 ASCII 条目名为主」。

**两个问题：**

1. 中文为主的库里这条路会主动放弃（判据不满足），但判据本身要先扫一遍全库统计
   非 ASCII 字节占比——白扫一次。
2. 即使判据满足，也是「扫一遍窄化 + 再扫一遍打分」= **两遍**，
   比原来的一遍还贵。实测 ASCII 库中文查询 1.18 ms。

删掉之后：1.18 ms → **680 µs**。

教训：**在已经只有一遍的扫描上加一层「预扫描」，永远是负收益。**

## 6. 中文搜索的现状与为什么停手

中文库（1 万条全中文条目）查询 ~980 µs。这个数字已经接近这个架构的下限：

- `str::contains` 对 UTF-8 是按字节比较的，中文查询的 needle 是 6~9 字节，
  在 300+ 字节的名字里做窗口比较，单条就要几百次字节比对；
- 一万条 × 四个字段 × 若干 needle = 上千万次比较，1 ms 是合理的结果；
- 唯一的进一步优化是建 n-gram 倒排索引，但那会把索引体积翻好几倍，
  而「中文条目一万条以上」的个人密钥库极其罕见。

**判断：不值得。** 真遇到中文为主的库，用户实际输入的是「银行」「阿里」这种 2 字词，
命中面窄，体验仍然是「打下去就有」。已经实测：中文短词 1.05 ms，可接受。

如果将来真要上 n-gram，接口不变，只换 `Index` 内部实现即可。

## 7. 复现

```bash
cargo test -p xz-core          # 50 项，应全绿
cargo run --release -p xz-bench
```

基准程序不依赖任何测试框架，直接 `Instant` 计时 + 多轮取中位/平均，
输出人可读的表格。故意没用 criterion：这类粗粒度场景不需要统计框架，
而且标准库手写能保证「用户跑得到的就是我们看到的」。
